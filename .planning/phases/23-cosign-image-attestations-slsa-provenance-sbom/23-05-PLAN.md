<objective>
Maintainer-driven HUMAN-UAT gate per D-06 two-stage rehearsal + Pitfall 12 fresh-machine UAT mandate. Stage 1 fires `docker.yml` via workflow_dispatch on the feature branch carrying Plans 23-01..04 to confirm the YAML compiles + cosign-installer + sigstore-pin-check all behave correctly (without exercising the tag-gated sign/attest steps). Stage 2 cuts a `v1.6.0-rc.0` pre-release tag, then runs all four SECURITY.md recipes from a fresh `docker run --rm -it ubuntu:24.04` container with no project state — empirically validating that ATTEST-01/02/03/04 deliver end-to-end AND the documented operator recipes are runnable from zero.

Purpose: D-06 explicitly rejects the "ship and amend if recipe broken" anti-pattern — the SECURITY.md recipes are operator-facing and a broken recipe documented at v1.6.0 is doc-rot in the wild. Pitfall 12 mandates this fresh-machine rehearsal style. RESEARCH §6 supplies the verbatim install + verify recipe + 13-row PASS/FAIL table shape. Stage 2 also runs a NEGATIVE test (Recipe 1 against `distroless/static:latest`) to empirically confirm the locked --certificate-identity-regexp is not too wide per Pitfall 1 (the regex's `johnzilla/blindjoin/.github/workflows/docker.yml@refs/tags/v.*` prefix should reject any image NOT signed by blindjoin's docker.yml).

This plan is intentionally larger than the standard 2-3 task budget — Task 2 covers 13+ distinct verification commands across two stages — because the bottleneck is human bandwidth (one maintainer, one sitting, one signed UAT artifact) and splitting fractures the rehearsal narrative. Stage 1 directly feeds Stage 2 (Stage 1's workflow_dispatch confirms YAML compiles; Stage 2's tag push exercises the full sign/attest pipeline against the same code). The fresh-machine UAT (Pitfall 12) and the negative test (Pitfall 1) intentionally re-run the verify procedures on a clean runner as cross-validation.
Output: One new file: `.planning/phases/23-cosign-image-attestations-slsa-provenance-sbom/23-05-UAT.md` capturing Stage 1 + Stage 2 evidence + GO/NO-GO verdict.
</objective>

<scope_justification>
This plan covers TWO stages (workflow_dispatch rehearsal + fresh-machine UAT against an rc.0 tag) plus 13+ distinct verification commands plus the UAT report write-up. Combined into one plan because the rehearsal is a single maintainer ratchet: Stage 1's run URL is captured in the same sitting as Stage 2's container session, and the rc.0 tag is cut once between them. Splitting Stage 1 / Stage 2 into separate plans would either (a) duplicate the UAT-report scaffold (one per plan) or (b) require Stage 2 to depend on a partially-written UAT report — both add overhead without saving context. The task count (3) stays within budget; Task 2 is large but each verification is a single-line CLI command with a pasteable output.
</scope_justification>
