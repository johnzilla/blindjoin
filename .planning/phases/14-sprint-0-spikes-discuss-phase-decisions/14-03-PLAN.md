    ## Decision #2 — Mixed vs segregated script-type rounds

    **Status:** ACCEPTED (mixed rounds)

    **Context:**
    Heterogeneous inputs (P2WPKH + P2TR + P2SH-P2WPKH) can either share one round queue (MIXED) or be segregated into per-script-type queues (SEGREGATED). The choice changes PKARR record schema and round-state-machine fork structure if overturned.

    **Decision:**
    MIXED rounds. One round queue accepts P2WPKH + P2TR + P2SH-P2WPKH inputs together (D-06). Coordinator round-state machine unchanged from v1.3 conceptually. Outputs remain single-script-type per round (D-07 — operator-configurable via `[bip] output_script_type` in `coordinator.toml`; default `p2wpkh`). No per-script-type minimum participant gate (D-08). Coordinator advertises the SUPPORTED SET over PKARR (`supported_script_types`) and `/round/info` but does NOT advertise per-round per-script-type registration counts (D-09 — REQUIREMENTS.md anti-feature, leaks correlation).

    **Consequences:**

    *Positive:*
    - FEATURES position: one queue defragments matchmaking; rare-script-type users can join sooner; total round-completion latency drops vs segregated.
    - ARCHITECTURE position: coordinator round-state machine carries v1.3 shape forward unchanged — minimal blast radius for the script-type dispatcher addition in Phase 16.

    *Negative:*
    - PITFALLS warns: a round with 1 P2TR input + 9 P2WPKH inputs is a chain-analysis fingerprint — the lone P2TR participant is trivially identifiable post-broadcast (V1.4-MOD-06). The liquidity bot's per-round type rotation (V1.4-MIN-02 mitigation; Phase 18 INTEG-01 success criterion #3) softens but does not eliminate this. The mixed-input fingerprint is a KNOWN LIMITATION documented in the v1.4 README §"Privacy Considerations" (CD-3 phrasing deferred to Phase 18 prose work).
    - **Carries to v1.5+ consideration:** If post-launch telemetry shows lone-rare-type participants being identified at unacceptable rates, segregated rounds re-open in v1.5. The data we need to make that call (round composition stats) is operator-facing logging, not on a public endpoint (D-09).

    *Neutral:*
    - STACK position: zero new mandatory dependencies for the MIXED path (the SEGREGATED path would also have added zero deps but required round-state-machine forking — strictly more code).

    ## Decision #3 — P2SH-P2WPKH `OwnershipProof` wire format

    **Status:** ACCEPTED (B2 base64 PSBT-input shape, `version: u8` envelope)

    **Context:**
    P2SH-P2WPKH inputs need to carry BOTH `final_script_sig` (the P2SH unwrap) AND `final_script_witness` (the P2WPKH signature). The current v1.3 `OwnershipProof { script_pubkey, witness, message }` shape carries only witness — insufficient. Three options were considered per .planning/research/SUMMARY.md:
    - B1: Tagged serde enum per script type.
    - B2: Single `psbt_input_b64: String` field holding `base64(bitcoin::psbt::Input)`.
    - B3: Optional-fields-with-default (keep old struct, add `final_script_sig: Option<Vec<u8>>`).

    **Decision:**
    B2 — base64 PSBT-input shape. `OwnershipProof.psbt_input_b64: String` holding `base64(bitcoin::psbt::Input)`. Natively carries `final_script_sig` + `final_script_witness` + any future PSBT fields without further wire-format changes. Aligns with the PSBT-everywhere round contract from v1.3.

    Envelope carries an explicit `version: u8` field for backwards-compat (D-12):
    - `version = 1` = v1.3 shape (witness-only; `psbt_input_b64` defaults via `#[serde(default)]`)
    - `version = 2` = v1.4 PSBT-input shape

    Coordinator branches on version (`match proof.version`); rejects unknown versions with `UnsupportedProofVersion`. WALLET-04 backwards-compat shim sends `version = 1` shape against pre-`0.2.0` PKARR records (Phase 17 work).

    Phase 15 ships the wire-format roundtrip test FIRST (D-13, v1.3 REPAIR-01 lesson #1 — non-negotiable phase boundary). Test cases enumerated in 14-CONTEXT.md D-13 (~10-15 cases total): self-roundtrip per script type; v1.3-shape backwards-compat; mismatched declared-vs-PSBT script type; unknown version; corrupted base64.

    **Consequences:**

    *Positive:*
    - ARCHITECTURE position: PSBT-everywhere alignment from v1.3 carries to v1.4 — coordinator and client both operate on PSBT objects everywhere except the wire envelope; B2 eliminates the round-trip-through-bytes friction B1/B3 introduced.
    - FEATURES position: B2 is forward-compatible to any PSBT field future BIPs add (e.g., taproot annexes, BIP-371 PSBT v2 fields) without further wire-format changes.

    *Negative:*
    - STACK position: B2 adds ~+100 bytes per P2WPKH proof vs the v1.3 witness-only shape (base64 overhead + PSBT envelope tags). Accepted as the cost of PSBT-everywhere alignment.
    - PITFALLS warns: base64-decode-error surface added to coordinator's validate path. Phase 15's D-13 test case #5 (corrupted base64 / truncated PSBT) gates this — must reject without panicking; must surface a typed decode error.

    *Neutral:*
    - ALL three options (B1, B2, B3) required a `version` field for v1.3 compat — that's not differentiating between options.

    **Rejected Alternatives:**
    - **B1 tagged serde enum:** Rejected. Forces a serde re-derive per added script type and couples wire shape to in-memory dispatch (the script-type enum becomes the wire schema). B2 decouples wire from dispatch.
    - **B3 optional-fields-with-default:** Rejected. Two fields (`final_script_sig: Option`, `witness: Witness`) with implicit "if both present, you're P2SH-P2WPKH" is ambiguous wire semantics; PSBT-shape (B2) is explicit by construction.
    - **Untagged serde enum:** Rejected. Untagged enums force serde to try deserializing each variant in order — slow and error-prone on malformed input.
