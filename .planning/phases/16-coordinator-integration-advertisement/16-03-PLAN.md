<byte_budget_arithmetic>
The 220-byte budget is binding at the PRODUCTION worst case (62-byte .onion address per Tor-native PROJECT constraint). Worst-case payload (default config, all-3-allowed, production .onion):

Pre-B3 (verbose names) projected: ~175 (base with .onion) + 30 (sst) + 16 (ost) = ~221 bytes — BREACHES the 220-byte warn.

Post-B3 compact-name savings:
- `"version"` → `"v"`: saves ~10 bytes
- `"denomination_sats"` → `"ds"`: saves ~16 bytes
- `"min_participants"` → `"mp"`: saves ~16 bytes
- `"status"` → `"st"`: saves ~7 bytes
- `"network"` → `"n"`: saves ~7 bytes
- Net savings: ~56 bytes

Production worst case (post-B3): ~119 (compact base) + ~30 (sst) + ~16 (ost) + ~48 extra (62-byte onion vs 14-byte localhost delta) = ~213 bytes. Comfortably under 220.
Dev worst case (post-B3, 14-byte `127.0.0.1:8080`): ~119 + ~30 + ~16 = ~165 bytes. Comfortably under 200.

`type` and `onion` retain verbose names: `type` is already 4 bytes (rename to `t` saves only 3 bytes and reduces schema identifiability for any future PKARR consumer); `onion` is load-bearing for v1.3 client resolver compat (renaming breaks the v1.3 `Partial { onion }` resolver per RESEARCH §V1.4-MOD-02).

If a 4th script type lands in v1.5+, `sst` alone breaches budget — re-evaluate the encoding (single-char codes, bitmask) per the deferred ideas section below.
</byte_budget_arithmetic>

<deferred_ideas>
**v1.5 PKARR encoding compaction (deferred per B3):**

If a 4th script type lands (e.g., bare-P2PK, P2SH-multisig) the `sst` CSV alone breaches the 220-byte budget. At that point re-evaluate the encoding:
- Option A: single-character script-type codes (e.g., `w` for p2wpkh, `t` for p2tr, `s` for p2sh-p2wpkh, plus the new one)
- Option B: bitmask integer (3 bits today, 4+ tomorrow)
- Option C: drop the CSV and ship a hash of the sorted set; clients fetch the full set out-of-band on demand
None of these are warranted for v1.4. The compact-name rename in this plan buys ~56 bytes of headroom — enough for ~2 more average-length kebab-case CSV components or 3-4 more compact fields.
</deferred_ideas>
