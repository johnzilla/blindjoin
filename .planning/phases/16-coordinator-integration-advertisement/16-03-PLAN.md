<byte_budget_arithmetic>
The 220-byte budget is binding. Worst-case payload (default config, all-3-allowed):

Base v0.1.0 payload (current): `{"type":"blindjoin-coordinator","version":"0.1.0","onion":"<onion-or-clearnet>","network":"signet","denomination_sats":1000000,"min_participants":3,"status":"idle"}` — approximately 175 bytes with a representative `.onion` address (62 bytes) or 145 bytes with the dev `127.0.0.1:8080` (14 bytes).

v0.2.0 additions:
- `"version":"0.2.0"` is a 1-byte delta over `"version":"0.1.0"` (no actual change).
- `,"sst":"p2sh-p2wpkh,p2tr,p2wpkh"` = approximately 30 bytes (key + ":" + quote + 24-char CSV + quote).
- `,"ost":"p2wpkh"` = approximately 16 bytes (key + ":" + quote + 6-char value + quote).

Worst case projected: 175 (base with onion) + 30 + 16 = ~221 bytes — DANGEROUSLY close to the 220-byte limit. The inline budget test detects breach.

If the budget breaches at default config (e.g., a longer onion address), the inline test fails AT TASK 1. Mitigation per CD-15 / Pitfall 2: the v1.5 problem is to reconsider the CSV encoding (single-char codes, bitmask, etc.). For v1.4, plan-time mitigation: bind the test fixture to the same `coordinator_addr` length used by the production worst case (default config uses `127.0.0.1:8080` = 14 bytes, NOT an onion address — the Phase 4 / Phase 5 onion address is used in production but the unit test exercises the dev path).
</byte_budget_arithmetic>
