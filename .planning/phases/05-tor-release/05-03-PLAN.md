Create `.github/workflows/` directory and write `release.yml`. This workflow:

1. Triggers on `push: tags: ['v*']`
2. Uses a 4-target matrix: linux-amd64, linux-arm64, macos-amd64, macos-arm64
3. Uses `cross-rs` for linux-arm64 (ubuntu-latest runner, aarch64-unknown-linux-gnu target)
4. Uses native `cargo` for the other three targets
5. Builds both `coordinator` and `client` binaries per target
6. Packages each target as `blindjoin-{name}.tar.gz` containing both binaries named with the target suffix
7. Uploads all four tarballs to GitHub Releases via `softprops/action-gh-release@v1`

```yaml
name: Release

on:
  push:
    tags: ['v*']

permissions:
  contents: write

jobs:
  build:
    name: Build ${{ matrix.name }}
    runs-on: ${{ matrix.runner }}
    strategy:
      fail-fast: false
      matrix:
        include:
          - name: linux-amd64
            runner: ubuntu-latest
            target: x86_64-unknown-linux-gnu
            use_cross: false
          - name: linux-arm64
            runner: ubuntu-latest
            target: aarch64-unknown-linux-gnu
            use_cross: true
          - name: macos-amd64
            runner: macos-latest
            target: x86_64-apple-darwin
            use_cross: false
          - name: macos-arm64
            runner: macos-latest
            target: aarch64-apple-darwin
            use_cross: false

    steps:
      - uses: actions/checkout@v4

      - uses: dtolnay/rust-toolchain@stable
        with:
          targets: ${{ matrix.target }}

      - uses: Swatinem/rust-cache@v2
        with:
          key: ${{ matrix.target }}

      - name: Install cross
        if: matrix.use_cross
        run: cargo install cross --git https://github.com/cross-rs/cross

      - name: Build coordinator
        run: |
          if [ "${{ matrix.use_cross }}" = "true" ]; then
            cross build --release --target ${{ matrix.target }} --bin coordinator
            cross build --release --target ${{ matrix.target }} --bin client
          else
            cargo build --release --target ${{ matrix.target }} --bin coordinator
            cargo build --release --target ${{ matrix.target }} --bin client
          fi

      - name: Package
        shell: bash
        run: |
          mkdir -p dist
          cp target/${{ matrix.target }}/release/coordinator \
             dist/coordinator-${{ matrix.name }}
          cp target/${{ matrix.target }}/release/client \
             dist/client-${{ matrix.name }}
          tar czf blindjoin-${{ matrix.name }}.tar.gz -C dist .

      - name: Upload to GitHub Releases
        uses: softprops/action-gh-release@v1
        with:
          files: blindjoin-${{ matrix.name }}.tar.gz
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

Write this file exactly. Do not add liquidity-bot to this workflow (it is Docker-only — no standalone binary release needed for the bot).

**Step 1 — docker/Dockerfile.client**: Create a cargo-chef multi-stage Dockerfile for the client binary, mirroring Dockerfile.coordinator:

```dockerfile
# docker/Dockerfile.client
# Multi-stage build using cargo-chef for dependency layer caching.

FROM lukemathwalker/cargo-chef:latest-rust-1 AS chef
WORKDIR /app

FROM chef AS planner
COPY . .
RUN cargo chef prepare --recipe-path recipe.json

FROM chef AS builder
COPY --from=planner /app/recipe.json recipe.json
RUN cargo chef cook --release --recipe-path recipe.json
COPY . .
RUN cargo build --release --bin client

FROM debian:bookworm-slim AS runtime
RUN apt-get update && apt-get install -y --no-install-recommends \
    ca-certificates \
    curl \
    && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY --from=builder /app/target/release/client /usr/local/bin/client
ENTRYPOINT ["/usr/local/bin/client"]
```

**Step 2 — .github/workflows/docker.yml**: Create the multi-arch Docker publish workflow.

The workflow triggers on both `v*` tags AND pushes to `main`. It builds three images (coordinator, client, liquidity-bot) using a matrix strategy. Each image is built for `linux/amd64,linux/arm64` using Docker Buildx + QEMU emulation.

Tags strategy:
- On `v*` tag: tag image as both `vX.Y.Z` and `latest`
- On `main` push: tag image as `main`

Use `docker/metadata-action@v5` to generate tags automatically.

```yaml
name: Docker

on:
  push:
    tags: ['v*']
    branches: [main]

permissions:
  contents: read
  packages: write

jobs:
  docker:
    name: Docker ${{ matrix.image }}
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        include:
          - image: coordinator
            dockerfile: docker/Dockerfile.coordinator
          - image: client
            dockerfile: docker/Dockerfile.client
          - image: liquidity-bot
            dockerfile: docker/Dockerfile.bot

    steps:
      - uses: actions/checkout@v4

      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - uses: docker/setup-qemu-action@v4

      - uses: docker/setup-buildx-action@v4

      - uses: docker/metadata-action@v5
        id: meta
        with:
          images: ghcr.io/${{ github.repository_owner }}/blindjoin-${{ matrix.image }}
          tags: |
            type=ref,event=branch
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=raw,value=latest,enable={{is_default_branch}}

      - uses: docker/build-push-action@v7
        with:
          context: .
          file: ${{ matrix.dockerfile }}
          platforms: linux/amd64,linux/arm64
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

NOTE on `on.push` with two keys: The YAML above uses `on.push.tags` and `on.push.branches` as sibling keys under `push`. This is valid GitHub Actions YAML — both branches and tags can be listed under the same `push` event. Do not duplicate the `push` key.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → GITHUB_TOKEN | Token has contents:write (release.yml) and packages:write (docker.yml) — scoped to minimum required |
| ghcr.io ← docker/build-push-action | Images are pushed publicly; no secrets embedded in image layers |
| cross-rs build environment | Cross-rs provides an isolated Docker container for aarch64 compilation; no host system contamination |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-11 | Tampering | Release artifacts (tar.gz binaries) | accept | GitHub Releases are tied to a specific commit SHA via the tag; no additional signing for v1 (future: sigstore/cosign for supply chain hardening in v2) |
| T-05-12 | Information Disclosure | GITHUB_TOKEN scope | mitigate | release.yml uses `permissions: contents: write` only; docker.yml uses `permissions: packages: write` only — no broad repo-scoped token |
| T-05-13 | Spoofing | cross-rs Docker image integrity | accept | cross-rs is installed from GitHub (--git https://github.com/cross-rs/cross) which pins to HEAD; acceptable for v1; future: pin to a specific commit SHA |
| T-05-14 | Denial of Service | QEMU ARM64 build timeout | mitigate | cargo-chef caches dependency layer; GHA cache (`cache-from: type=gha`) further reduces rebuild; Pitfall 6 (RESEARCH.md) documents this as acceptable for v1 |
| T-05-15 | Elevation of Privilege | Workflow trigger on any v* tag push | mitigate | Only users with write access to the repo can push tags; GitHub branch protection rules can require signed tags for mainnet releases |
</threat_model>
