Wire `.github/workflows/release.yml`'s `build` job for SIGN-01 (cosign blob signature) + SIGN-02 (SLSA v1.0 provenance attestation). Four structural changes: (1) add an explicit job-level `permissions:` block with `contents: write`, `id-token: write`, `attestations: write` and an auditor-grepable comment header; (2) install cosign 2.6.3 via the Phase 23 SHA-pinned `sigstore/cosign-installer@v3.10.1`; (3) sign the tarball with `cosign sign-blob --yes --bundle` and attest its build provenance with `actions/attest-build-provenance@v3.2.0`; (4) modify the existing `softprops/action-gh-release` step to ship as `draft: true` with a 4-file `files:` list. RESEARCH §3.2 correction is load-bearing — `actions/attest-build-provenance@v3.2.0` has NO `output-name` input; a separate `mv` step relocates the bundle from `${RUNNER_TEMP}/...` to `blindjoin-linux-amd64.tar.gz.sigstore`.

Purpose: SIGN-01 + SIGN-02 are the load-bearing CI deliverables of Phase 24. SIGN-01 produces the `.bundle` cosign signature (consumed by operators via `cosign verify-blob --bundle`); SIGN-02 produces both the GitHub Attestations API record (consumed via `gh attestation verify`) and the `.sigstore` bundle file (consumed via `cosign verify-attestation --bundle`). The four Release assets the CI uploads (`tarball + .sha256 + .bundle + .sigstore`) are the artifact half of SC#1 + SC#2. `draft: true` (D-07) is load-bearing because it stops operators from seeing a release missing its PGP `.asc` companion before the maintainer flips it out of draft per docs/RELEASING.md.

Output: One modified file: `.github/workflows/release.yml` (~50 net new lines counting comment blocks; ~5 lines modified on the existing softprops step). Phase 23 Plan 23-03's `sigstore-pin-check` gate at ci.yml:292-326 continues to enforce the two new sigstore SHA pins automatically — no new CI gate required.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions OIDC token → Sigstore Fulcio | The OIDC token issued via `id-token: write` is exchanged at Fulcio for a short-lived signing cert bound to the workflow identity. Without job-level `id-token: write`, sign fails opaquely with "fulcio: 400 Bad Request" (Pitfall 2). |
| Workflow file → operator-side identity-regexp | The identity regexp documented in Plan 24-03's SECURITY.md (`release\.yml@refs/tags/v.*`) is what binds CI signatures to the right workflow file. A drift between this Task's workflow filename and Plan 24-03's documented regex breaks operator verification silently. |
| Action SHA pins → supply-chain integrity | The two sigstore action SHAs are the trust roots for the signing toolchain. SHA drift (or a malicious force-push at the action repo against an unpinned tag) lets an attacker substitute code into the sign path. Pinned 40-hex SHAs + the sigstore-pin-check gate at ci.yml:292-326 close this. |
| `${RUNNER_TEMP}` → workspace root | The `mv` step (Task 3) crosses this boundary. The bundle is moved from a runner-temp path to the workspace root where softprops can pick it up. A runner-temp path collision (extremely unlikely given GHA's per-run isolation) would manifest as a wrong file uploaded. |
| Tag namespace → release identity | The workflow-level tag gate `if: startsWith(github.ref, 'refs/tags/')` at release.yml:66 is what prevents non-tag pushes from producing signed artifacts. The `--certificate-identity-regexp 'release\.yml@refs/tags/v.*'` operator-side recipe (Plan 24-03) is what binds verification to the same constraint. |
