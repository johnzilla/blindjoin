```yaml
name: CI

on:
  pull_request:
    branches: [main]

jobs:
  test:
    name: cargo test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - uses: Swatinem/rust-cache@v2
      - name: Run tests
        run: cargo test --workspace

  clippy:
    name: cargo clippy
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
        with:
          components: clippy
      - uses: Swatinem/rust-cache@v2
      - name: Run clippy
        run: cargo clippy --workspace -- -D warnings

  audit:
    name: cargo audit
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - name: Install cargo-audit
        run: cargo install cargo-audit --locked
      - name: Run audit (deny high and critical)
        run: cargo audit --deny high --deny critical
```

Key constraints (per D-04, D-05):
- Audit uses `--deny high --deny critical` — NOT `--deny warnings`. Low and medium advisories are informational only and do not fail the job.
- Three separate jobs (test, clippy, audit) so GitHub shows distinct status checks — this allows branch protection to require each one independently.
- Cache is NOT used in the audit job (cargo install should not be cached — it installs a tool, not a dependency).
- `pull_request: branches: [main]` — CI only fires on PRs targeting main (per D-03: PR-triggered, not tag-triggered).

```markdown
# Enabling Branch Protection for CI Gates

After merging the CI workflow (`.github/workflows/ci.yml`), configure GitHub branch
protection to make the status checks required. This is a one-time manual step —
GitHub does not allow programmatic branch protection from within a workflow run.

## Why This Is Necessary

The `ci.yml` workflow runs `cargo test`, `cargo clippy`, and `cargo audit` on every
pull request. Without branch protection rules, the checks run but do not block merging.
Required status checks make the CI gate mandatory.

## Setup Steps

1. Go to **Settings** → **Branches** in this repository on GitHub.
2. Under **Branch protection rules**, click **Add rule** (or edit the existing `main` rule).
3. In the **Branch name pattern** field, enter: `main`
4. Check **Require status checks to pass before merging**.
5. Check **Require branches to be up to date before merging**.
6. In the status check search box, add the following checks (they appear after at least one
   CI run has completed):
   - `cargo test`
   - `cargo clippy`
   - `cargo audit`
7. Optionally check **Require a pull request before merging** if you want reviews enforced too.
8. Click **Save changes**.

## Status Check Names

These names come from the `name:` field of each job in `.github/workflows/ci.yml`:

| Status Check | CI Job | What It Enforces |
|---|---|---|
| `cargo test` | `test` | `cargo test --workspace` must pass |
| `cargo clippy` | `clippy` | `cargo clippy --workspace -- -D warnings` must pass |
| `cargo audit` | `audit` | No high or critical CVEs in dependency tree |

## Notes

- Status checks only appear in the GitHub search box after the workflow has run at least once.
  Open a draft PR to trigger the first run before configuring protection.
- The `check` jobs in `release.yml` and `docker.yml` are separate from these PR checks
  and do not need to be added to branch protection rules.
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → cargo registry | Cargo fetches deps from crates.io; network access in untrusted environment |
| Workflow YAML → GitHub permissions | Workflow requests `contents: write` (release) and `packages: write` (docker) |
| cargo audit → RustSec advisory DB | Pulls advisory DB from GitHub — if DB is unavailable, audit may fail or skip |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Tampering | cargo install cargo-audit | mitigate | Use `--locked` flag: `cargo install cargo-audit --locked` — ensures reproducible install from Cargo.lock, prevents supply-chain substitution |
| T-06-02 | Spoofing | dtolnay/rust-toolchain@stable | accept | Action is from a trusted, widely-used author; pinning to `@stable` (not a SHA) is standard practice for this action across the ecosystem. Pin to SHA if paranoid is a future hardening option. |
| T-06-03 | Elevation of Privilege | workflow permissions | mitigate | ci.yml uses default (read) permissions — no `permissions:` block needed. release.yml already scoped to `contents: write` only. docker.yml scoped to `packages: write` only. No workflow has `write-all`. |
| T-06-04 | Denial of Service | RustSec DB unavailability | accept | If RustSec advisory DB is unavailable, `cargo audit` fails the CI run. This is acceptable — a failing audit blocks the PR, preventing a silent bypass. Operator can re-run when DB is available. |
| T-06-05 | Information Disclosure | GITHUB_TOKEN in workflow env | accept | `GITHUB_TOKEN` is repository-scoped, auto-rotated per workflow run, and never exposed in logs. Risk is low. |
</threat_model>
