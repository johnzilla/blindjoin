## Decision #1 — `bip322` crate adopt vs extend

**Status:** ACCEPTED (ADOPT bip322 = "=0.0.10") — flipped from default ACCEPTED (EXTEND) per D-01's conditional-flip rule because Sprint-0-A returned `GO:` across all three D-02 gates.

**Context:**
`shared/src/bip322.rs` currently holds 133 LOC of custom BIP-322 primitives (P2WPKH-only sign + verify, plus the script-type-NEUTRAL `bip322_message_hash` / `build_bip322_to_spend` / `build_bip322_to_sign` helpers — V1.4-MOD-07 single source of truth). v1.4 needs P2TR and P2SH-P2WPKH support. Two options were on the table per `.planning/research/SUMMARY.md` §"Open Decision #1":

- **ADOPT** the upstream `bip322` crate (v0.0.10 from rust-bitcoin org) and wrap its `verify_simple(&Address, message, Witness)` API behind a thin adapter in `shared/src/bip322/`.
- **EXTEND** our custom impl by splitting `shared/src/bip322.rs` into `shared/src/bip322/{mod.rs, p2wpkh.rs, p2tr.rs, p2sh_p2wpkh.rs}` per D-04.

Sprint-0-A probed three GO-criteria gates (D-02): (1) `bitcoin = 0.32.x` in the transitive tree, (2) `cargo audit` clean on the new edges, (3) adapter sketch under 50 LOC with zero lossy conversions. The captured verdict line in `.planning/research/sprint-0-A.md:199` reads verbatim:

> GO: all three D-02 gates PASS — bip322 v0.0.10 pulls in bitcoin v0.32.8 (gate 1), cargo audit is clean on the full graph including the three new transitive edges (gate 2), and the wire-shape adapter sketches at 26 LOC with zero lossy conversions (gate 3).

**Decision:**
Adopt `bip322 = "=0.0.10"` (exact pin, CI grep gate per the v1.3 REPAIR-02 pattern) as a wrapped dependency in `shared/src/bip322/`. Phase 15 lands the 26-LOC adapter sketched in `.planning/research/sprint-0-A.md` (lines 145-175) bridging the crate's `verify_simple(&Address, message, Witness)` to our wire shape `(scriptPubKey, witness, message)`. The script-type-NEUTRAL primitives (`bip322_message_hash`, `build_bip322_to_spend`, `build_bip322_to_sign`) STAY in `shared/src/bip322/` as V1.4-MOD-07's single source of truth — the crate's analogous `bip322::to_spend` / `to_sign` helpers are NOT used directly. Three new transitive crates enter the v1.4 dependency graph (`bip322 v0.0.10`, `snafu v0.8.9`, `snafu-derive v0.8.9` proc-macro); all are cargo-audit clean at adoption time.

Phase 15 (BIP322-01..04) implements per D-04's module split with crate-backed verify: `mod.rs` (public API + `ScriptType` dispatcher), `p2wpkh.rs` (carried over from existing impl), `p2tr.rs` (new — crate-backed verify; sign path is ours regardless per Consequences below), `p2sh_p2wpkh.rs` (new — crate-backed verify with HASH160 + redeem-script unwrapping). Per-script-type property tests against `basic-test-vectors.json` ship in Phase 15 BIP322-04.

**Consequences:**

*Positive:*
- **FEATURES position (now load-bearing):** Standardised upstream impl, smaller verify-surface we own forever. ARCHITECTURE researcher notes the crate's `verify_simple` covers P2WPKH + P2TR + P2SH-P2WPKH in one API call; one adapter, one error mapping, one `cargo audit` edge to watch.
- **PITFALLS softer concern:** Ongoing fixes shipped by upstream rust-bitcoin maintainers; we inherit BIP-322 correctness patches without code changes on our side. Sprint-0-A's gate 2 (`cargo audit` clean) plus the v1.3 REPAIR-02 exact-pin CI grep gate keep dependency drift under control.
- **D-21 invariant preserved at Phase 14 boundary:** Adoption is a Phase 15 implementation decision, not a Phase 14 commit. This ADR records the choice; `shared/` is untouched by Phase 14.

*Negative:*
- **PITFALLS warns:** the `bip322` crate is at v0.0.10 (young, no SemVer 1.x commitment). Breaking-change exposure carries into v1.4 and v1.5; mitigation is the exact pin (`bip322 = "=0.0.10"`) plus the CI grep gate. If the crate ships a 1.0 release before v1.5 starts, re-evaluate adoption posture per the Deferred Ideas marker in 14-CONTEXT.md.
- **STACK position:** three new transitive crates enter the graph (`bip322`, `snafu`, `snafu-derive`). Acceptable per Sprint-0-A gate 2 (zero new advisories) but worth tracking — `snafu-derive` is a proc-macro and compile-time-only, so runtime attack surface is the bip322 + snafu pair.
- **D-05 asymmetry (load-bearing — both adopt and extend paths):** Per STACK researcher, `bdk_wallet` does NOT ship BIP-322 signing (rust-bitcoin/bdk issue #150 open since May 2023). The client signer is OURS regardless of this decision. Adopt-vs-extend only affects the verify path in `shared/`, never the sign path. ADOPT halves the verify surface we own; it does nothing for the sign surface. The reduction in owned LOC is a verify-side win only — Phase 17 WALLET-02 still implements the client sign path (in v1.4 via `bdk_wallet::Wallet::sign(...)` on a BIP-322-shaped PSBT per Decision #4, NOT via the `bip322` crate's signing API).

*Neutral:*
- Either path keeps `bip322_message_hash` / `build_bip322_to_spend` / `build_bip322_to_sign` (script-type-NEUTRAL) as the SINGLE source of truth for message-hash math (V1.4-MOD-07). The crate's `bip322::to_spend` / `to_sign` helpers would be wrapped by an adapter, not replace these. This preserves byte-deterministic alignment with our hand-rolled message-hash output across both verify (crate) and sign (ours) sides.
- ARCHITECTURE researcher notes either path satisfies Phase 15's BIP322-04 per-script-type property test against `basic-test-vectors.json`. The test pins by commit SHA from `bitcoin/bips` and runs against our verify entry point regardless of whether the crate or our own code does the inner work.

**Rejected Alternatives:**
- **EXTEND (D-01 conservative default):** Rejected because Sprint-0-A passed all 3 gates cleanly (D-02), satisfying the D-01 conditional-flip. Under EXTEND we would have owned ~205 LOC after Phase 15's module split (133 existing + ~70 new for P2TR + P2SH-P2WPKH per STACK researcher's estimate); ADOPT reduces this to the 26-LOC adapter plus the unchanged script-type-NEUTRAL helpers.
- **Decide-AFTER-spike (no pre-commitment):** Rejected per D-03 ambiguous-policy. Leaves Phase 15 planning ambiguous if the spike returns INCONCLUSIVE; D-03 makes the verdict binary at the spike boundary so downstream planning is deterministic.
- **Defer to v1.5 (skip multi-script in v1.4):** Rejected. The v1.4 milestone IS multi-script BIP-322 support per PROJECT.md §"Current Milestone"; deferring defeats the milestone goal.

## Decision #2 — Mixed vs segregated script-type rounds

**Status:** ACCEPTED (mixed rounds)

**Context:**
Heterogeneous inputs (P2WPKH + P2TR + P2SH-P2WPKH) can either share one round queue (MIXED) or be segregated into per-script-type queues (SEGREGATED). FEATURES researcher recommended MIXED (matchmaking lifts; defragments queues; rare-script-type users join sooner). PITFALLS researcher recommended SEGREGATED (eliminates the heterogeneous-input chain-analysis fingerprint). The choice changes PKARR record schema and round-state-machine fork structure if overturned. Neither Sprint-0 spike addresses this decision — it is resolved by 14-CONTEXT.md's discussion-locked rationale (D-06..D-10), recorded here.

**Decision:**
MIXED rounds. One round queue accepts P2WPKH + P2TR + P2SH-P2WPKH inputs together (D-06). Coordinator round-state machine carries forward unchanged from v1.3 conceptually — only the validate-utxo dispatch fans out by script type. Outputs remain single-script-type per round (D-07 — operator-configurable per-coordinator via `[bip] output_script_type` in `coordinator.toml`; default `p2wpkh`; same output type for every round this coordinator runs). No per-script-type minimum participant gate (D-08 — defeats the reason MIXED was chosen). Coordinator advertises the SUPPORTED SET over PKARR (`supported_script_types`) and `/round/info` but does NOT advertise per-round per-script-type registration counts (D-09 — REQUIREMENTS.md anti-feature, leaks correlation). At validate-utxo time the coordinator derives `script_type` from the on-chain `txout.script_pubkey` and cross-checks against the client-declared `script_type` (D-10, CRIT-01 mitigation, code-review checked in Phase 16).

Implementation lives in Phase 16 (ADVERT-01..03 + CRIT-01). The ADR records the policy here as the input contract for Phase 16 planning.

**Consequences:**

*Positive:*
- **FEATURES position:** One queue defragments matchmaking; rare-script-type users (P2TR adopters, P2SH-P2WPKH legacy holders) join sooner; total round-completion latency drops vs segregated. The matchmaking lift is the biggest user-visible win for the milestone.
- **ARCHITECTURE position:** Coordinator round-state machine carries the v1.3 shape forward unchanged — minimal blast radius for the script-type dispatcher addition in Phase 16. The v1.3 `full_round::*` cross-phase invariant gate stays cheap to verify (no state-machine fork to test).
- **STACK position:** Zero new mandatory dependencies for the MIXED path. The SEGREGATED path would also have added zero deps but required round-state-machine forking — strictly more code, strictly more test surface.

*Negative:*
- **PITFALLS warns (V1.4-MOD-06):** A round with 1 P2TR input + 9 P2WPKH inputs is a chain-analysis fingerprint — the lone P2TR participant is trivially identifiable post-broadcast. The liquidity bot's per-round type rotation (V1.4-MIN-02 mitigation; Phase 18 INTEG-01 success criterion #3) softens but does not eliminate this. The mixed-input chain-analysis fingerprint is a KNOWN LIMITATION; the v1.4 README §"Privacy Considerations" will document it candidly. Exact phrasing is deferred to Phase 18 prose work per CD-3 — the ADR records the limitation here without pre-writing the README copy.
- **Carries to v1.5+ consideration:** If post-launch telemetry shows lone-rare-type participants being identified at unacceptable rates, segregated rounds re-open in v1.5. The data needed to make that call (round composition stats) is operator-facing logging only, not on a public endpoint (D-09 invariant).

*Neutral:*
- Output type stays single-per-round (D-07); users who want a different output type pick a different coordinator. This is PKARR's whole point per PROJECT.md §"Core Value" — coordinators are disposable and replaceable via DHT.
- The CRIT-01 cross-check (D-10) is independent of the mixed/segregated decision. Whichever path was chosen, the coordinator would still need to derive `script_type` from the on-chain UTXO and reject mismatched client declarations.

**Rejected Alternatives:**
- **Segregated rounds (PITFALLS position):** Rejected per D-06. The trade-off was the per-script-type matchmaking-fragmentation tax vs the chain-analysis-fingerprint tax. The MIXED path takes the fingerprint tax and mitigates with liquidity-bot rotation + operator transparency in the README §"Privacy Considerations". Re-evaluable in v1.5 if post-launch telemetry warrants.
- **Per-script-type minimum participant gate (e.g., `min_p2tr = 3`):** Rejected per D-08. Defeats the reason MIXED was chosen — would re-fragment the queue and re-introduce SEGREGATED's matchmaking tax under a different label.
- **Per-script-type ban tracking:** Anti-feature per REQUIREMENTS.md Out-of-Scope. Leaks correlation across rounds; design invariant is uniform `OutPoint`-keyed ban list. NOT a v1.5 candidate either.
- **Per-script-type rate limits:** Anti-feature per REQUIREMENTS.md Out-of-Scope. Defeats the Tor-safe `GlobalKeyExtractor` (v1.2 Phase 8); per-script-type buckets would require client identity beyond the script-type declaration. NOT a v1.5 candidate either.
- **Mixed output script types (Wasabi 2.0.3-style per-participant output choice):** Rejected per REQUIREMENTS.md Out-of-Scope. Separate output-policy milestone, v1.5+ if it surfaces.

## Decision #3 — P2SH-P2WPKH `OwnershipProof` wire format

**Status:** ACCEPTED (B2 base64 PSBT-input shape, `version: u8` envelope)

**Context:**
P2SH-P2WPKH inputs need to carry BOTH `final_script_sig` (the P2SH unwrap) AND `final_script_witness` (the P2WPKH signature). The current v1.3 `OwnershipProof { script_pubkey, witness, message }` shape (defined at `shared/src/protocol.rs` lines 13-28) carries only `witness` — insufficient for P2SH-P2WPKH. Three options were considered per `.planning/research/SUMMARY.md`:

- **B1:** Tagged serde enum per script type (`OwnershipProof::P2wpkh { ... }`, `OwnershipProof::P2tr { ... }`, `OwnershipProof::P2shP2wpkh { ... }`).
- **B2:** Single `psbt_input_b64: String` field holding `base64(bitcoin::psbt::Input)` regardless of script type.
- **B3:** Optional-fields-with-default (keep v1.3 struct, add `final_script_sig: Option<Vec<u8>>`).

Neither Sprint-0 spike addresses this decision — it is resolved by 14-CONTEXT.md's discussion-locked rationale (D-11..D-13), recorded here.

**Decision:**
B2 — base64 PSBT-input shape. The v1.4 `OwnershipProof` envelope carries `psbt_input_b64: String` holding `base64(bitcoin::psbt::Input)`. Natively carries `final_script_sig` + `final_script_witness` + any future PSBT fields (taproot annexes, BIP-371 PSBT v2 fields, etc.) without further wire-format changes. Aligns with the PSBT-everywhere round contract carried forward from v1.3.

Envelope carries an explicit `version: u8` field for backwards-compat per D-12:

- `version = 1` = v1.3 shape (witness-only; `psbt_input_b64` defaults via `#[serde(default)]`)
- `version = 2` = v1.4 PSBT-input shape

Coordinator branches on version (`match proof.version`); rejects unknown versions with `UnsupportedProofVersion`. WALLET-04 backwards-compat shim sends `version = 1` shape against pre-`0.2.0` PKARR records (Phase 17 work).

Phase 15 ships the wire-format roundtrip test FIRST per D-13 (v1.3 REPAIR-01 lesson #1, non-negotiable phase boundary) BEFORE either coordinator or client uses the new shape. Test cases (~10-15 total per 14-CONTEXT.md D-13):

1. `version = 2` self-roundtrip for all 3 script types (P2WPKH, P2TR, P2SH-P2WPKH) → passes.
2. `version = 1` (v1.3 shape) deserialises into v1.4 type with `script_type` defaulted to P2WPKH → passes (backwards-compat).
3. `version = 2` with mismatched declared `script_type` vs PSBT-input contents (e.g., declares P2TR but the PSBT has a P2WPKH redeem script) → rejects with `WireFormatMismatch`.
4. `version = 3` (or any unknown version) → rejects with `UnsupportedProofVersion`.
5. `version = 2` with corrupted base64 / truncated PSBT → rejects without panicking; surfaces typed decode error.

Implementation lives in Phase 15 (BIP322-01..04). The ADR records the test-discipline requirement here as the input contract for Phase 15 planning.

**Consequences:**

*Positive:*
- **ARCHITECTURE position:** PSBT-everywhere alignment from v1.3 carries to v1.4 — coordinator and client both operate on PSBT objects everywhere except the wire envelope; B2 eliminates the round-trip-through-bytes friction B1/B3 introduced.
- **FEATURES position:** B2 is forward-compatible to any PSBT field future BIPs add (taproot annexes, BIP-371 PSBT v2 fields, future witness-version extensions) without further wire-format changes. Decision #5 in v1.5+ (if it arrives) would extend semantics inside the PSBT envelope, not the envelope itself.
- **D-13 enforcement:** Phase 15's wire-format roundtrip test ships FIRST per v1.3 REPAIR-01 lesson #1 — the wire-format gate is a non-negotiable phase boundary, not an after-the-fact integration check. This is the load-bearing discipline that closed REPAIR-01 cleanly in v1.3.

*Negative:*
- **STACK position:** B2 adds approximately +100 bytes per P2WPKH proof vs the v1.3 witness-only shape (base64 overhead + PSBT envelope tags). Accepted as the cost of PSBT-everywhere alignment; per-round bandwidth impact is bounded by the participant count (~25 participants × ~100 bytes = ~2.5 KB per round, negligible vs the round's other payloads).
- **PITFALLS warns:** base64-decode-error surface added to the coordinator's validate path. Phase 15's D-13 test case #5 (corrupted base64 / truncated PSBT) gates this — must reject without panicking; must surface a typed decode error. Phase 16 ADVERT-01..03 inherits this gate.

*Neutral:*
- ALL three options (B1, B2, B3) required a `version` field for v1.3 backwards-compat — that's not differentiating between options, only the wire shape inside the envelope differs.
- Per-script-type sanity check (declared `script_type` matches the PSBT contents) is required regardless of wire shape; B2 makes it explicit at decode time (PSBT contents are parsed), B1 collapses it to serde tag-matching, B3 leaves it implicit. B2's explicit decode is the most testable.

**Rejected Alternatives:**
- **B1 tagged serde enum:** Rejected. Forces a serde re-derive per added script type and couples wire shape to in-memory dispatch (the script-type enum becomes the wire schema). B2 decouples wire from dispatch — the wire carries a PSBT regardless of how the coordinator's internal `ScriptType` enum evolves in v1.5+.
- **B3 optional-fields-with-default:** Rejected. Two fields (`final_script_sig: Option<Vec<u8>>`, `witness: Witness`) with implicit "if both present, you're P2SH-P2WPKH" is ambiguous wire semantics; PSBT-shape (B2) is explicit by construction. Also re-introduces the v1.3 wire-format ambiguity that REPAIR-01 lesson #1 closed.
- **Untagged serde enum:** Rejected. Untagged enums force serde to try deserialising each variant in order — slow and error-prone on malformed input; defeats the typed decode-error requirement (Consequences/negative item #2).

## Decision #4 — bdk_wallet 2.3 P2TR sign path

**Status:** ACCEPTED (bdk path) — per Sprint-0-B's `PASS:` verdict and `bdk path` recommendation.

**Context:**
Phase 17 WALLET-02 needs to sign BIP-322 ownership proofs for all 3 script types. P2WPKH is settled by Decision #1 (crate-backed verify; bdk_wallet sign). P2SH-P2WPKH falls out of the same path (BIP-143 sighash over unwrapped redeem script). P2TR is the open question: does `bdk_wallet 2.3`'s PSBT signer produce a verifiable 64-byte Schnorr keypath witness for a BIP-322-shaped PSBT, or do we need to hand-roll the sign path?

Sprint-0-B exercised the 8-step PoC at `client/examples/spike-p2tr.rs` (spike branch only, per CD-4): deterministic `[0u8; 32]` seed → BIP-86 (`tr(.../86'/1'/0'/0/*)`) descriptor → BIP-322 `to_spend` + `to_sign` via `shared::bip322::*` script-type-NEUTRAL primitives → PSBT with `SignOptions { trust_witness_utxo: true }` (load-bearing per v1.3 Phase 12) and the canonical BIP-322 `witness_utxo` (value = 0, script_pubkey = P2TR SPK) → `wallet.sign(...)` → extract the 64-byte Schnorr keypath signature → `secp256k1::verify_schnorr` against the BIP-341 keyspend sighash.

The captured verdict line in `.planning/research/sprint-0-B.md:315` reads verbatim:

> PASS: bdk_wallet 2.3's PSBT signer produces a valid 64-byte Schnorr keypath witness for a BIP-322 `to_sign` PSBT under a BIP-86 (`tr(.../86'/1'/0'/0/*)`) descriptor when `SignOptions { trust_witness_utxo: true }` is set and `witness_utxo` is populated with the canonical BIP-322 to_spend output (value = 0, script_pubkey = P2TR SPK). Step 6 (bdk sign) returned `Ok(finalized=true)`, step 7 recovered the 64-byte sig from `final_script_witness`, and step 8 (`secp256k1::verify_schnorr`) returned `Ok(())`.

The captured recommendation line at `sprint-0-B.md:323` reads `bdk path`.

**Decision:**
Phase 17 WALLET-02 uses `bdk_wallet 2.3`'s PSBT signer for the P2TR (BIP-86) descriptor, via `wallet.sign(&mut psbt, SignOptions { trust_witness_utxo: true, ..Default::default() })` against a BIP-322-shaped PSBT whose `inputs[0].witness_utxo` is populated with the canonical BIP-322 to_spend output (`TxOut { value: 0, script_pubkey: <P2TR SPK> }`). The recovered 64-byte Schnorr keypath signature is the wire-format witness.

**No new `shared/src/bip322/p2tr.rs::sign_p2tr_keypath` function ships in v1.4.** D-15's 80-LOC manual fallback budget is freed and retired for v1.4 (D-15 stays on the books as a v1.5 reconsideration target if bdk_wallet ever regresses on taproot keyspend).

**Phase 17 implementation note (load-bearing for WALLET-02):** Sprint-0-B surfaced that bdk_wallet 2.3 finalises single-key taproot keyspend inputs into `psbt.inputs[0].final_script_witness[0]` (a single 64-byte witness element), NOT into `psbt.inputs[0].tap_key_sig` (which is cleared during finalisation). Phase 17's witness-extraction code MUST check both fields and prefer whichever bdk populated — parallels the existing P2WPKH extraction fallback at `client/src/wallet.rs:277-285`. This is documented inline in `sprint-0-B.md:317-319` and is part of WALLET-02's input contract.

The verify path in `shared/` is independent of this decision (Decision #1 governs it via the adopted `bip322` crate).

**Consequences:**

*Positive:*
- **STACK position:** Zero LOC added to `shared/` for the P2TR sign path; `bdk_wallet`'s PSBT signer is already exercised by v1.3's P2WPKH path (battle-tested codepath; REPAIR-01 forensics confirmed its segwit signing under `trust_witness_utxo: true`). The 80-LOC manual-fallback budget under D-15 is freed.
- **FEATURES position:** Single sign-path abstraction across all 3 script types (P2WPKH, P2TR, P2SH-P2WPKH) — all go through `bdk_wallet::Wallet::sign(...)` with the same `SignOptions { trust_witness_utxo: true }` shape. Phase 17 WALLET-02's per-script-type code is descriptor selection only; signing is uniform.
- **ARCHITECTURE position:** `bdk_wallet` 2.3 finalisation behaviour for single-key taproot is now characterised (witness lands in `final_script_witness[0]`, not `tap_key_sig`) — the dual-path extraction pattern parallels the existing P2WPKH extraction at `client/src/wallet.rs:277-285`. Symmetric code on both sides.

*Negative:*
- **PITFALLS warns:** Tight coupling to `bdk_wallet 2.3` internals; any bdk minor-version bump risks silent sighash drift or finalisation-path changes. Mitigations: (a) exact pin `bdk_wallet = "=2.3.x"` already enforced; (b) Phase 15 BIP322-04 per-script-type property test against the official BIP-322 vectors catches drift at CI; (c) `client/src/wallet.rs:277-285`'s existing dual extraction (and the analogous Phase 17 pattern) means a future bdk that moves the sig back into `tap_key_sig` does NOT break us.
- **STACK position (carries to v1.5):** If v1.4 lifecycle adds an Arti workspace-constraint conflict that requires migrating off `bdk_wallet`, the P2TR sign path becomes a swap target. D-15's manual fallback (`shared/src/bip322/p2tr.rs::sign_p2tr_keypath`, 80-LOC budget) is the pre-spec'd swap-in. v1.5+ candidate, not a v1.4 risk.

*Neutral:*
- Both paths (bdk and manual) route through `shared::bip322::bip322_message_hash` for message hashing (V1.4-MOD-07 single source of truth) — no fork. Sprint-0-B's PoC validates this explicitly: `client/examples/spike-p2tr.rs` step 3 calls `bip322_message_hash(MESSAGE)` and step 4 calls `build_bip322_to_sign(&to_spend)`, both from `shared::bip322`.
- Verify path is unaffected by this decision (Decision #1 governs it). The D-05 asymmetry recorded in Decision #1 stands: ADOPT or EXTEND, bdk path or manual fallback — the verify and sign surfaces are decoupled.

**Rejected Alternatives:**
- **Manual fallback (D-15 pre-spec):** Rejected because Sprint-0-B returned `PASS:` and recommendation `bdk path`. The 80-LOC budget in `shared/src/bip322/p2tr.rs::sign_p2tr_keypath` is freed for v1.4. The fallback stays on the books as the v1.5 swap target if bdk_wallet regresses (D-15 + D-16 test discipline remain valid pre-spec material).
- **Re-test in Phase 17 (defer the decision):** Rejected per D-14 binary-by-design. The whole point of Sprint-0-B was to settle this before Phase 17 plan-phase; deferring re-introduces planning ambiguity downstream and bloats Phase 17's scope.
- **Wait for bdk_wallet to add a BIP-322 sign API (issue #150):** Rejected. rust-bitcoin/bdk issue #150 has been open since May 2023 (per D-05) with no committed timeline. v1.4 cannot block on it; if the upstream API lands in bdk 2.4 or 2.5, v1.5 picks it up as an internal simplification (one-line swap inside `client/src/wallet.rs`).
- **Wrap a different crate (e.g., a third-party Schnorr-sign helper):** Rejected. Manual `secp256k1::sign_schnorr` is the same primitive any wrapper would call; we already depend on `secp256k1` transitively via `bitcoin 0.32.x`. No third-party wrapper would buy anything we don't already have.
